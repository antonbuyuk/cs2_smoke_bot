## Postgres на хосте, а не в docker compose

**Контекст.** На VPS (Hetzner-style, 144.91.73.230) уже работает соседний проект `food-bot` (Telegram-бот с pet-проектом владельца), который использует системный PostgreSQL 16, установленный через `apt`. Перенос соседа в docker — задача в чужом коде с риском сломать прод.

**Решение.** cs2-bot тоже использует хостовый PostgreSQL 16. В docker-compose Postgres-сервиса нет. Контейнер `admin` коннектится через `host.docker.internal:host-gateway` (в DATABASE_URL — `172.17.0.1:5432`).

**Почему не альтернативы:**
- *Postgres в compose, отдельный кластер* — два инстанса PG на одном VPS = двойной memory footprint и две точки бэкапа. На 4GB RAM VPS нерационально.
- *Postgres в compose с external volume на хостовой PG* — невозможно, у двух процессов конфликт на один data dir.
- *Перенос foodbot в compose тоже* — out of scope, чужой проект.

**Последствия:**
- В `docker-compose.yml` нужен `extra_hosts: ["host.docker.internal:host-gateway"]`.
- Бэкапы делаем на уровне БД (`pg_dump cs2_bot`), не всего кластера — у соседа свой бэкап-режим.
- Миграции PG (major-version upgrade) синхронизируем с владельцем foodbot.

## listen_addresses = 'localhost,172.17.0.1', а не '*'

**Контекст.** До нашего вмешательства Postgres слушал на `0.0.0.0:5432` — порт торчал в публичный интернет, ufw был `inactive`, провайдерский firewall не настроен. Брутфорс или CVE ловили бы за дни.

**Решение.** В `postgresql.conf`:
```
listen_addresses = 'localhost,172.17.0.1'
```
Postgres слушает только loopback (для соседних админских утилит) и docker bridge gateway (для контейнеров на этой же машине).

**Почему не альтернативы:**
- *ufw allow from docker-bridge, deny 5432* — включать ufw на проде по SSH без rescue-консоли = риск отрубить доступ. Listen-фильтр обратимее.
- *Оставить `*` + pg_hba whitelist по IP* — pg_hba не защищает от TCP-handshake'а; брутфорс соединений всё равно проходит.

**Последствия:**
- Внешние админские клиенты (DBeaver с домашнего IP) больше не работают напрямую — нужен SSH-tunnel: `ssh -L 5432:localhost:5432 root@vps`.
- Foodbot пришлось перенастроить с `144.91.73.230:5432` на `172.17.0.1:5432` (его `.env`).

## DATABASE_URL → 172.17.0.1, а не публичный IP

**Контекст.** Foodbot изначально ходил в БД через публичный IP VPS (`144.91.73.230`), что требовало `listen_addresses = *` и держало порт открытым в интернет.

**Решение.** Все приложения на этой же VPS ходят в Postgres через `172.17.0.1` (docker0 gateway).

**Почему:**
- Не требует открытого порта снаружи.
- Трафик не покидает виртуальную сеть docker — быстрее, не зависит от hairpin NAT.
- IP стабильный (172.17.0.1 — стандарт docker), не меняется при смене провайдера.
- Пароль не идёт через интернет-маршрут (у foodbot был `sslmode=disable`).

**Последствия:** в pg_hba нужно правило для каждой docker-сети, использующей коннект:
- `172.17.0.0/16` для cs2_bot (default bridge — наш контейнер будет в нём)
- `172.18.0.0/16` для foodbot (его compose создал отдельную сеть `food-bot_default`)

## Bind mount, а не named volume для storage/uploads

**Контекст.** Медиа-файлы (картинки/видео гранат) лежат в `storage/uploads/`. Нужно: переживать пересоздание контейнера, бэкапиться `tar`/`rsync`, быть видимыми с хоста для отладки.

**Решение.** В compose:
```yaml
volumes:
  - /opt/cs2-bot/storage/uploads:/app/storage/uploads
```

**Почему не named volume:**
- Named volume лежит в `/var/lib/docker/volumes/...` — путь не очевиден, бэкапить надо через docker, восстанавливать сложнее.
- Bind mount даёт прямой `ls /opt/cs2-bot/storage/uploads/` — отладка тривиальна.
- Размер тома не лимитирован отдельной ФС, использует свободное место хоста.

**Последствия:** `chown 1000:1000 /opt/cs2-bot/storage` при первом деплое (UID node-юзера в node:20-alpine).

## ghcr.io, а не Docker Hub

**Контекст.** Нужен registry для образа `cs2-bot-admin`, куда GH Actions будет пушить. Pull с VPS через `docker pull`.

**Решение.** GitHub Container Registry (`ghcr.io/abuyuk10/cs2-bot-admin`). Образ публичный.

**Почему не Docker Hub:**
- Авторизация через GH Actions нативная — `secrets.GITHUB_TOKEN` дефолтный, не нужен отдельный аккаунт.
- Нет лимитов на pull (Docker Hub бесплатный — 100 pulls/6h на анонима).
- Образ живёт в одном месте с кодом — связь очевидна.

**Последствия:** на VPS `docker login ghcr.io` не нужен (образ публичный); если перейдём на private — придётся хранить PAT в `.env`.

## nginx на хосте, а не Caddy в compose

**Контекст.** Порт 80/443 на VPS уже занят системным nginx, который проксирует foodbot на свой бэкенд. Нужно добавить vhost для cs2.awawa-chef.com.

**Решение.** Используем существующий nginx. Добавляем server-block с `proxy_pass http://127.0.0.1:3000;`. TLS — через certbot (`certbot --nginx`).

**Почему не Caddy/Traefik в compose:**
- Невозможно — порты 80/443 уже заняты nginx'ом соседа.
- Перенос соседа на тот же compose = заваривать чужую кашу (см. decision о Postgres).

**Последствия:**
- При смене API/маршрутов админки нужно править `/etc/nginx/sites-available/cs2.awawa-chef.com.conf` руками.
- Renewal сертификатов certbot — общий cron на хосте, не в compose.

## Telegram initData, а не OAuth/email

**Контекст.** Аудитория — 1 владелец + 5 знакомых. Все уже в Telegram, бот существует.

**Решение.** Логин через Telegram Login Widget на странице `/admin/login`. Сервер валидирует HMAC `initData` по `BOT_TOKEN`, сохраняет `user_id` в httpOnly cookie. Allowlist по `ADMIN_IDS` env.

**Почему не альтернативы:**
- *Email + password* — никто не будет регистрироваться, плюс reset-flow, плюс XSS/SQLi attack surface.
- *OAuth (GitHub/Google)* — у целевой аудитории нет кросс-сервисной идентичности; для корешей это лишние клики.
- *Magic link* — Telegram уже делает это нативно, без email-инфраструктуры.

**Последствия:**
- `BOT_TOKEN` нужен в admin'е для HMAC-валидации (даже если бот заморожен).
- На admin-странице должен быть подключён `https://telegram.org/js/telegram-widget.js` — внешняя зависимость.

## Бот заморожен, не удалён

**Контекст.** В монорепо есть `apps/bot` (Grammy + state machines). После party mode решено: вся работа с гранатами идёт через `apps/admin` (веб + PWA), бот не нужен MVP-юзерам.

**Решение.** Бот не деплоим, не запускаем. Код остаётся в репо в текущем виде. `package.json` скрипт `dev:bot` рабочий — для отладки локально.

**Почему не удалить:**
- В `apps/bot/src/index.ts` есть рабочий media-group буфер (debounce 500ms) и handlers для добавления гранат — могут пригодиться, если соберёмся вернуть бот-флоу.
- Удаление = lock-in решения "бот не нужен никогда". Заморозка — обратимо.

**Последствия:** в CI собираем только admin (`npm run build:admin`). Боту не выделяем отдельный Dockerfile.

## Пятиуровневый фильтр оставлен (карта → сторона → линия → тип → сложность)

**Контекст.** Sally в party mode предлагала упростить до 3-4 уровней. После обсуждения с John (метрики) и Mary (competitive scan) — решено оставить.

**Решение.** Пятиуровневый фильтр сохраняется. UX — drill-down с auto-advance: выбор на каждом уровне сразу подгружает следующий (без кнопки "далее").

**Почему не сократить:**
- Сложность (`easy/medium/hard`) — критичная ось для flashcard-режима ("учу только easy перед матчем").
- Линия отдельно от типа — у одной линии могут быть smoke/flash/HE с разной механикой.

**Последствия:** на низком разрешении (мобила в портретной) фильтр в две строки. ОК для MVP.

## Global allowlist middleware вместо opt-in

**Контекст.** До 2026-05-07 защита pages-маршрутов в `apps/admin` была opt-in: `middleware/auth.ts` (для `isAuthenticated`) и `middleware/auth-admin.ts` (для `isAdmin`) подключались вручную через `definePageMeta({ middleware: ... })` на каждой странице. Архитектурный текст говорил «защищает только `/admin/*` маршруты», хотя такого префикса в коде не существовало — реальные admin-страницы лежат в `/users`, `/moderation`, `/settings/*`. Любая новая admin-страница без явного `definePageMeta` молча оказывалась бы публичной.

**Решение.** Один глобальный middleware `middleware/auth.global.ts` (Nuxt подключает `*.global.ts` ко всем маршрутам автоматически) с двумя списками:
```
PUBLIC_PATHS = ['/', '/grenades']     // guest OK
ADMIN_PATHS  = ['/users', '/moderation', '/settings'] // требует isAdmin
```
Всё остальное требует `isAuthenticated`. `middleware/auth-admin.ts` удалён — его логика поглощена.

**Почему не альтернативы:**
- *Оставить opt-in* — security regress: добавление новой admin-страницы требует помнить о `definePageMeta`. На код-ревью один раз пропустим — публичная админка.
- *Префикс `/admin/*` для всех админ-страниц* — потребует переименовать `/users`, `/moderation`, `/settings`, переписать ссылки и навигацию. Цена выше, чем у allowlist по именам.
- *Только серверная защита (Nitro middleware)* — недостаточно: страницы рендерятся на клиенте даже без данных, юзер видит layout/UI, что выглядит как баг и подсказывает структуру админки.

**Последствия:**
- Для нового pages-маршрута достаточно создать `.vue` файл — он автоматически требует auth. Public-маршрут — добавить путь в `PUBLIC_PATHS`. Admin-only — в `ADMIN_PATHS`.
- `definePageMeta({ middleware })` больше не нужен ни на одной странице (кроме спецлогики, которой нет).
- `developMode` (env `DEVELOP_MODE=true`) по-прежнему обходит весь middleware — для локальной разработки без Telegram-логина.

## "Линап дня" отвергнут

**Контекст.** Идея random/curated линапа на главной — типичный engagement-хук в продуктах вроде Anki/Duolingo.

**Решение.** Не делаем. Главная = список "в работе" из flashcard-deck'а юзера.

**Почему:**
- 6 юзеров — random не даст вариативности (за неделю прокрутишь весь каталог).
- "В работе" — конкретный action, "посмотри случайное" — не action.
- Add'ить позже легко, удалять hooks из UX тяжело.

**Последствия:** на главной нужно состояние "в работе пусто" — приглашение прочекать гранаты по фильтру.
